# Автоматическая синхронизация и быстрый экран

Включение: `PUT /api/v1/workspaces/{workspace_id}/stores/{store_id}/sync-schedule`.
Нужны действующая сессия с MFA, роль владельца и подключённый магазин.
Тело: `{"enabled":true,"sources":["catalog","sales","finance"],"recent_days":7,"load_history":true}`.
Отключение `enabled:false` останавливает будущие задания; уже начатые не отменяет.
Курсоры истории сохраняются. Для Basic-токена остатки недоступны и запросы не отправляются.

1. Сначала последние 7 завершённых дней (можно выбрать 7–30), затем более старые периоды.
2. Продажи: доступные последние 90 дней. Финансы: с 29.01.2024, по месячным порциям назад.
3. Свежие обновления чередуются с порциями истории, чтобы долгие паузы WB не оставляли историю без загрузки.
4. Продажи обновляются по `lastChangeDate` с перекрытием 3 дня. Финансы — повторная загрузка последних
   30 дней, раз в неделю сверка 90 дней: WB не предоставляет здесь курсор изменений.
5. Внутренние интервалы: каталог 6 часов, продажи 15 минут, финансы 6 часов. Это частота готовности
   нашего планировщика, а не обещание частоты WB. Общий Redis gate магазина и заголовки WB всегда
   имеют приоритет. Другие токены магазина не создают независимые лимиты.
6. Финансовая страница начинается со 100 000 строк; при превышении 64 MiB уменьшается
   без сдвига курсора, новая попытка только после паузы. Уменьшенная страница может снова
   вырасти до 100 000 при небольшом ответе.
   Слишком большой исторический месяц делится на меньшие интервалы. Объём одного задания ограничен.

`GET .../sync-schedule` показывает план и границу оставшейся истории.
`GET .../analytics?date_from=YYYY-MM-DD&date_to=YYYY-MM-DD&limit=100` выдаёт:

- `sales`: продажи, возвраты, разницу в штуках, предварительные суммы и число пропущенных цен;
- `daily`: продажи/возвраты по дням с загруженными событиями;
- `abc`: товары с положительным вкладом по чистому количеству, группы A/B/C с границами 80/95%;
  товар, пересекающий порог, остаётся в предыдущей группе;
- `finance`: суммы выбранных полей отчёта отдельно по валютам, без смешивания валют;
- `coverage`, `period_complete`, `available`, `partial_sources`: полнота и наличие данных.

Сумма к перечислению не является прибылью: все расходы, себестоимость и реклама пока не учтены.
ABC этого старого маршрута — по штукам. Отдельные новые финансовые методы поддерживают
ABC по выручке и предварительному вкладу в прибыль: [PROFIT.md](PROFIT.md).
Отрицательные и нулевые вклады не участвуют в положительном рейтинге ABC.
Продажи по курсору изменений не расширяют покрытие полной истории.

Записи и дневные показатели шифруются AES-GCM с привязкой к магазину, пространству, источнику,
периоду/ключу записи и набору данных. PostgreSQL RLS включён и принудителен для новых таблиц.
Кэш Redis тоже содержит только шифротекст, живёт 15 минут и обновляется по версии опубликованных
данных/прогрессу первого импорта. Авторизация и RLS проверяются до чтения кэша.
Обычные периоды 7/30/90 дней заранее прогреваются фоновым заданием каждые 5 минут.

Повторные страницы не увеличивают итог. При исправлении события старый вклад вычитается, новый
добавляется. Публикация записей и показателей происходит в одной транзакции. Первый импорт имеет
явно отмеченный предварительный набор; последующее незавершённое обновление сохраняет предыдущий
полный результат. Паузы WB не снимаются вручную. Импорт файлов/Excel в этом этапе не добавлен.

Локальный экран: http://127.0.0.1:8010/. Стенд использует существующий отдельный доступ к одному
магазину и не изменяет требования обычного API. Миграция `0004_sync_plans_metrics` добавляет
таблицы/поля, не удаляет существующие данные.
