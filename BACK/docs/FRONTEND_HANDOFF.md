# Подключение первых экранов фронтенда

## Обновление API — 23 октября 2026: возвраты продавцу WB

- Новый источник `returns`: `/sync`, `/sync-schedule`, `/data/returns`. Включён в новые
  расписания; существующие нужно сохранить заново с `returns` в источниках.
- `GET .../insights/returns?date_from&date_to` — возвраты товаров продавцу (брак, невыкуп,
  неопознанный товар и т. п.) за период: `totals`, `by_type`, `by_status`, `daily`, `products`.
  День возврата — дата готовности к выдаче продавцу (`date_basis: "ready_for_pickup"`),
  при её отсутствии — дата заказа.
- `pickup` — текущее состояние, **не зависит от периода**: товары, которые лежат в ПВЗ
  и не забраны (`items` с `expires_on` и `days_left`, ближайший срок первым), счётчики
  `expiring_soon` (0–3 дня), `expired`, `in_transit` (ещё едут в ПВЗ). После окончания
  хранения WB может утилизировать товар — это главный блок для действий.
- Неизвестные дни — `null`; `as_of` — время последней успешной загрузки. История — 180 дней
  (глубина у WB не описана). Код маркировки, стикер и номер задания не сохраняются.
- Заявки покупателей на возврат (`/api/v1/claims`) пока не подключены: нужно право токена
  «Возвраты покупателями», его код в токене ещё не подтверждён.

## Обновление API — 23 октября 2026: воронка карточек WB

- Новый источник `funnel`: `/sync`, `/sync-schedule`, `/data/funnel`. Включён в новые
  расписания по умолчанию; существующие расписания нужно явно обновить.
- `GET .../insights/funnel?date_from&date_to` — переходы в карточку, корзины, заказы,
  выкупы, отмены/возвраты (WB объединяет их), избранное, суммы и конверсии.
  Есть `totals`, `daily`, `products` (до 500, флаг `products_truncated`).
- Это переходы в карточку, **не показы товара в выдаче**. Отдельного CTR здесь нет.
- `buyouts_by: "order_date"`: выкупы относятся к дню заказа, не к дню продажи,
  поэтому данные отличаются от `/insights/buyouts`. `buyout_percent` = выкупы /
  (выкупы + отмены/возвраты), без товаров в пути. Общие конверсии считаются по сумме
  счётчиков, не средним процентов карточек; при нулевом знаменателе — null.
- `buyouts_maturing_from` предупреждает о последних 14 днях. Это эвристика PERK,
  **не гарантия WB**, что более старые данные окончательны.
- `status`: `ready`, `partial`, `no_data`; `known_days`/`period_days` описывают покрытие.
  Суммы totals — только за известные дни; неизвестный день — null, загруженный пустой — 0.
  При смешении валют суммы null. Чтение из снимков, фоновые обновления, ETag/304.
- WB обновляет данные примерно раз в 2 часа. PERK перечитывает последний месяц раз
  в 6 часов; начальная история (до 360 дней) загружается постепенно с лимитами WB.
  При долгой загрузке начальный отчёт остаётся `no_data`, а не показывает ложные нули.


## Обновление API — 23 октября 2026: выкупы за любой период

- `GET .../insights/buyouts?date_from&date_to` — выкупы, возвраты и чистые штуки по дням
  и товарам с 29.01.2024, **по дате продажи**. Каждый день берётся из одного источника
  (`daily[].source`): `sales_report` — отчёт о продажах (последние ~90 дней, включая дни,
  которых ещё нет в еженедельном отчёте); `finance_report` — финансовые отчёты
  (детализация реализации), сгруппированные по `saleDt`; `null` — данных нет (значения null).
- День из финотчёта считается известным, только если отчёты загружены минимум на
  `report_lag_days` (30) дней после него: WB включает продажу в отчёт с опозданием.
- Суммы не складываются между источниками: `amounts[]` разделены по `basis`
  (`buyer_paid` — цена покупателя из отчёта о продажах, `retail_price` — розничная цена из
  финотчёта) и валюте. Штуки (`totals`, `daily`, `products`) сопоставимы.
- `status`: `ready`, `partial` (часть дней неизвестна), `preparing` (идёт фоновое обновление
  агрегатов, обычно несколько минут после обновления сервера), `no_data`.
- Сезонность теперь считается по дате продажи (`basis: "report_sales_by_sale_date"`).
- `/analytics?sales_basis=reports` не менялся: там по-прежнему дата отчёта.

## Обновление API — 23 октября 2026: заказы WB

- Новый источник синхронизации `orders` (`POST .../sync`, `PUT .../sync-schedule`,
  `GET .../data/orders`). По умолчанию включён в расписание. Хранится 90 дней, как у WB.
- `GET .../insights/orders?date_from&date_to` — заказы, отмены, % отмен, средний чек,
  выкупы, возвраты и % выкупа по дням (`daily`) и товарам (`products`, до 500).
  Работает как остальные снимки: ETag/304, `freshness.stale`.
- `null` означает «неизвестно» (нет завершённой загрузки за день или у заказа нет цены),
  а не ноль. `status`: `ready` — оба отчёта покрывают весь период; `partial` — суммы
  только за известные дни (`orders_known_days`, `sales_known_days`); `no_data`.
- `buyout_rate_percent` — выкупы / неотменённые заказы за те же дни
  (`buyout_rate_basis: "period_ratio"`), показывается только при полном покрытии периода.
- Дашборд: новое поле `orders` (вчера и сумма за 7 дней). В старых снимках до пересчёта
  его может не быть — поле необязательное.
- Прогноз остатков и план поставки: `demand_basis` = `orders` (неотменённые заказы покрывают
  окно) или `buyouts` (как раньше).

  могут остаться текстовыми; клиент не должен считать любой не-JSON ответ финансовыми данными.
- OpenAPI описывает `ErrorResponse` и новые маршруты команды. Обновите сгенерированный
  клиент перед подключением новых экранов.

## Регистрация, вход и коды подтверждения

Регистрация открытая. Коды — 6 цифр; хранятся на сервере только как хеш.
Не записывайте пароли, коды, токены, MFA-секреты и recovery-коды в логи и аналитику.
Ошибки кодов возвращают `detail` объектом: `{"code": "...", "message": "...", ...}`.

**Регистрация** (аккаунт создаётся только после кода из письма):

1. `POST /auth/register` — email, password (≥15 символов), workspace_name, client →
   202 `{challenge_id, channel, destination, expires_in, resend_after}`. Ответ одинаковый,
   даже если адрес уже зарегистрирован (тогда письмо без кода).
2. `POST /auth/register/verify` — challenge_id, code, client → 201 токены, сессия
   подтверждена. Повтор письма: `POST /auth/register/resend` (не чаще раза в 60 с).

**Вход** — пароль, затем второй фактор:

1. `POST /auth/login` — email, password, client → токены ограниченной сессии,
   `mfa_required: true` и `second_factor`:
   - `challenge` — куда автоматически отправлен код (Telegram/SMS, а без номера — почта);
     отсутствует, если подключено приложение-аутентификатор;
   - `available` — способы: email, telegram, sms, totp, recovery;
   - `delivery_error` — код не ушёл; запросите его через `/auth/mfa/send`.
2. `POST /auth/mfa/send` `{channel?}` — повторить или выбрать другой способ.
   Почта недоступна, если у аккаунта есть телефон или приложение (`channel_not_allowed`).
3. `POST /auth/mfa/verify` `{code}` — 6 цифр или recovery-код `rc_...` →
   **новые** токены; прежние ограниченные токены сразу перестают работать.

**Подтверждение действий** — после входа код действует 5 минут:

- `403 {"code": "step_up_required", "strong": false|true}` →
  `POST /auth/step-up/send` `{channel?}` → `POST /auth/step-up/verify` `{code}` → повторить запрос.
- `strong: true` (подключение/замена/проверка/отключение токена магазина, смена телефона,
  отключение приложения, новые recovery-коды) принимает только Telegram/SMS, приложение
  или recovery-код, не почту.
- `403 {"code": "strong_factor_required"}` → предложить привязать телефон.

**Телефон** (рекомендуется сразу после регистрации, обязателен для подключения магазина):

1. `POST /auth/phone` `{phone, channel: "telegram"|"sms"}` — номер в любом виде
   (`8 900 …`, `+7 (900) …`), сейчас разрешены российские номера.
2. `POST /auth/phone/confirm` `{code}` → `recovery_codes` при первом сильном факторе:
   показать один раз и предложить сохранить.
3. `PUT /auth/phone/channel` — сменить Telegram ↔ SMS.

**Прочее:** приложение-аутентификатор — `POST /auth/totp/setup`, `/auth/totp/confirm`,
`DELETE /auth/totp`; новые recovery-коды — `POST /auth/recovery-codes`;
смена пароля — `POST /auth/password` (нужен свежий код); забыли пароль —
`POST /auth/password/forgot` → `/auth/password/reset`. Сброс пароля по почте не отменяет
второй фактор: при следующем входе всё равно нужен телефон или приложение.

`GET /auth/me`: email_verified, phone (маскированный), phone_channel, totp_enabled,
strong_factor_enabled, session_mfa_verified, step_up_valid, strong_step_up_valid.
После подтверждения входа: `GET /workspaces`, затем `/workspaces/{workspace_id}/stores`.
Обновление сессии — `POST /auth/refresh`, выход — `/auth/logout`.

Локально коды не отправляются наружу: письма — в Mailpit (`http://127.0.0.1:8025`
при запуске с compose.dev.yaml) или в `docker compose logs api`; коды Telegram/SMS — в лог api.

## Next.js / веб

- `client: "web"` при register/login, `credentials: "include"`.
- Access/refresh в HttpOnly cookies; Bearer одновременно не отправляйте.
- Записывающие запросы и refresh требуют `X-CSRF-Token` из ответа авторизации
  или cookie perk_csrf. После refresh используйте новый CSRF-токен.
- Точный Origin фронта добавляется в CORS_ORIGINS. Используйте одинаковое имя хоста:
  localhost в обоих приложениях или 127.0.0.1 в обоих.
- Серверные вызовы Next.js требуют отдельного проектирования передачи сессии;
  не делайте незащищённый proxy авторизации.

## Expo / мобильный клиент

- `client: "mobile"`, Authorization Bearer, SecureStore для токенов.
- Refresh передаёт refresh_token в JSON, затем заменяет оба токена.
- Обновление токенов выполняется одним общим запросом: параллельные повторные refresh
  могут считаться повторным использованием и отозвать сессию.
- API привязан к loopback компьютера. Для телефона нужен отдельно настроенный локальный
  сетевой доступ/порт/файрвол. localhost на телефоне не является компьютером с API.

## Первые графики

Префикс магазина: `/workspaces/{workspace_id}/stores/{store_id}`.

- `GET .../analytics?date_from=YYYY-MM-DD&date_to=YYYY-MM-DD&sales_basis=auto`:
  сводка продаж, дни, ABC по количеству и покрытие. Для длинной истории auto выбирает
  финансовый источник; statistics и finance нельзя складывать. Строгий response_model
  старого analytics ещё предстоит добавить. Контракты:
  [AUTO_SYNC_ANALYTICS.md](AUTO_SYNC_ANALYTICS.md), [sales-history.md](sales-history.md).
- `GET .../finance/summary?date_from=YYYY-MM-DD&date_to=YYYY-MM-DD`:
  типизированные сводка/дни/товары, предварительная прибыль до налогов, issues и покрытие.
- `GET .../finance/abc?date_from=YYYY-MM-DD&date_to=YYYY-MM-DD&metric=revenue`:
  ABC по выручке; contribution — по вкладу до внешних расходов магазина.
- `GET .../sync-schedule`, `GET .../sync-runs/{run_id}` — состояния фоновой загрузки.
- `GET .../data/{source}` — нормализованные строки с пагинацией.

Деньги считайте через decimal-библиотеку; Number используйте только для координат графика
и округлённого отображения. null — неизвестный результат, не ноль. Не дорисовывайте
нулевые продажи вне подтверждённого покрытия. Финансовые графики используют report_date.
preparing можно опрашивать через несколько секунд; ready может сопровождаться неполным
расчётом. ABC incomplete — рейтинг известной части, а не полный ассортимент.

Импорт: [COST_IMPORTS.md](COST_IMPORTS.md). Расчёты: [PROFIT.md](PROFIT.md).
Частичный график: [FINANCE_PARTIAL.md](FINANCE_PARTIAL.md). `ready` с `is_partial=true`
показывается вместе с индикатором загрузки. Заменяйте снимок целиком; повторяйте запрос
при изменении records_processed/pages_processed и после завершения или ошибки задачи.
Статус и оставшиеся задачи: [STATUS.md](STATUS.md).

## Быстрая загрузка экранов (обязательно к соблюдению)

Тяжёлые отчёты не считаются в момент запроса. Сервер хранит готовые зашифрованные снимки
и пересчитывает их в фоне после каждой загрузки данных WB, изменения себестоимости,
расходов, налогов или целей, а также после полуночи. Чтение снимка — одна строка из БД.

Каждый такой ответ содержит `freshness`:

- `stale: false` — данные актуальны;
- `stale: true` — данные магазина изменились, свежая версия уже считается. Показывайте
  полученные цифры сразу с небольшим индикатором «обновляется» и повторите запрос
  через 3–5 секунд, пока не придёт `stale: false`. **Не показывайте экран загрузки.**
- `computed_at` — когда посчитан снимок (подпись «обновлено в 10:42»).

Правила для фронта:

1. **Первый экран — один запрос** `GET .../dashboard`: продажи вчера и за 7 дней, выручка
   и прибыль за 30 дней (до и после налогов), счётчики и срочные товары по остаткам,
   три главные находки аудита потерь.
2. **ETag.** Ответы снимков содержат заголовок `ETag`. Сохраните его вместе с данными и
   отправляйте `If-None-Match` при повторном запросе: если ничего не изменилось, сервер
   вернёт пустой `304` — используйте сохранённую копию.
3. **Кэш на клиенте.** Сохраняйте последние ответы (TanStack Query persist /
   AsyncStorage на мобильном) и показывайте их мгновенно при открытии приложения, затем
   обновляйте в фоне. В мобильном приложении храните кэш только для текущего пользователя
   и очищайте при выходе.
4. **Стандартные периоды мгновенны.** Без `date_from/date_to` используются последние
   30 дней — этот снимок готов заранее. Нестандартный период считается один раз при первом
   запросе (может занять несколько секунд), затем тоже отдаётся из снимка.
5. **Предзагрузка.** После дашборда в фоне запросите аудит, юнит-экономику и прогноз
   остатков — к моменту перехода на экран они уже будут в кэше клиента.
6. Ответы больше 1 КБ приходят сжатыми (gzip); ответы `/auth/*` не сжимаются.
7. `ETag` доступен браузеру и с другого origin, `If-None-Match` разрешён CORS. Ответы
   помечены `Cache-Control: no-store` (финансовые данные не попадают в HTTP-кэш браузера),
   поэтому ETag храните вместе с данными в своём кэше и отправляйте сами.

Качество данных — отдельно от свежести снимка (`freshness.stale` говорит только о кэше):

- финансы: `status`, `is_partial` (идёт импорт), `period_covered` (весь период загружен),
  `products_truncated` (слишком много товаров для одного расчёта — итоги неполные);
- продажи на главной: `sales.status` = ready / partial / no_data и `known` у каждого дня.
  Неизвестный день — `units: null, amount: null`; рисуйте пропуск, а не ноль;
- остатки: `stock_as_of` — когда WB реально отдал остатки, `source_stale` — старше двух
  дней (прогноз и тревоги не доверяют таким данным), `observed_days` — сколько дней истории.

Период: передавайте обе даты или ни одной. Начало не раньше 29.01.2024, без будущих дат,
не длиннее трёх лет — иначе 422.

`/auth/logout-all` требует подтверждённой сессии; сессия «только пароль» может завершить
лишь саму себя через `/auth/logout`.

## Новые разделы

Префикс магазина: `/workspaces/{workspace_id}/stores/{store_id}`. Все суммы — decimal-строки,
`null` — неизвестно (не ноль). Чтение доступно всем участникам, изменения — владельцу.

| Экран | Запрос | Что внутри |
|---|---|---|
| Главная | `GET .../dashboard` | Сводка первого экрана (см. выше) |
| Где вы теряете деньги | `GET .../insights/audit` | Находки: штрафы, хранение и товары без продаж, убыточные товары, нет себестоимости, упущенная выручка, логистика, возвраты; у каждой сумма, доля выручки, товары, объяснение |
| Юнит-экономика | `GET .../finance/unit-economics?margin_target=15&status=loss` | На штуку: цена, комиссия WB, логистика, хранение, приёмка, штрафы, себестоимость, налог, прибыль, маржа; статус profitable/marginal/loss/unknown |
| Симулятор цены | `POST .../finance/simulate` `{nm_id, price, cost_price?, units_expected?}` | Прибыль на штуку при новой цене, точка безубыточности, сколько продать для прежней прибыли |
| Чистая прибыль | `GET .../finance/net-profit` | Прибыль до налогов, НДС, налог, чистая прибыль, пояснения к расчёту |
| Налоги | `GET/PUT .../tax-settings`, `DELETE .../tax-settings/{date}` | Режим (none, usn_income, usn_income_expense, profit), ставка, НДС, база (revenue — цена покупателя, payout — выплата WB) с датой начала |
| Остатки | `GET .../inventory/forecast?status=critical` | Остаток, в пути, скорость продаж, дней запаса, дата окончания, статус, упущенная выручка, спрос по складам и размерам |
| План поставки | `POST .../inventory/supply-plan` `{lead_time_days, cover_days, safety_days, nm_ids?}` | Сколько везти, разбивка по складам (по спросу покупателей) и размерам, объяснение формулы |
| История остатков | `GET .../inventory/history?date_from&date_to&nm_id?` | Остаток по дням (снимки копятся с момента обновления) |
| Сезонность | `GET .../insights/seasonality?nm_id?` | Индекс спроса по месяцам; `unavailable` с причиной, если истории меньше года |
| Журнал событий | `GET/POST .../events`, `DELETE .../events/{id}` | Отметки на графиках: смена цены, акция, реклама, поставка, контент |
| План/факт | `GET .../goals?month`, `PUT .../goals`, `DELETE .../goals/{month}/{metric}` | Цель, факт на вчера, линейный прогноз на конец месяца |

Скорость продаж и прогноз остатков основаны на **выкупах** WB (заказы в API пока не
загружаются). Дни, когда товара не было, не занижают скорость продаж.

## Уведомления (телефон)

- `GET /notifications?unread_only&before&limit` — лента и `unread_count`;
  `POST /notifications/{id}/read`, `POST /notifications/read-all`.
- `GET/PUT /notifications/settings` — утренняя сводка (час по Москве), тревоги,
  каналы Telegram и push.
- `POST /notifications/devices` `{token: "ExponentPushToken[...]", platform}` после входа
  (expo-notifications); `DELETE` с тем же телом при выходе.
- `POST /notifications/telegram/link` → `url` (t.me/бот?start=…, 10 минут) — открыть
  ссылку, пользователь нажимает «Старт». `DELETE /notifications/telegram` — отвязать.

Тревоги: товары заканчиваются (раз в день на магазин), резкое падение продаж, токен WB
истекает в течение недели, ошибка загрузки. В Telegram и push уходят утренняя сводка
и важные тревоги; лента хранит всё 90 дней. Локально сообщения пишутся в лог worker.
