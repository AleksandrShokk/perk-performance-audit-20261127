# Потребность по направлениям

Сайт: Поставки → По кластерам. Для WB направление — нативный regionName
отгрузки из истории остатков; для Ozon — нативный cluster_id. Названия площадок
и кабинетов не объединяются в придуманный общий справочник. Общая потребность
по магазину остаётся прежним отдельным расчётом. Излишки одного направления
не закрывают дефицит другого, а короб округляется отдельно для каждого направления.

Архитектура бэка: app/modules/supplies/destinations/{normalize,models,jobs,service,router,schemas}.py.
UI: DestinationPanel внутри существующей feature supplies, общие таблицы,
параметры, детали товара, оформление плана и экспорт используются повторно.
Общая математика остаётся в supplies.service.from_demand.

## Данные Ozon

/v1/analytics/stocks уже вызывается для FBO. Импорт сохраняет ads_cluster,
cluster_name и cluster_id. Для SKU + cluster_id остатки складываются по
уникальному warehouse_id + placement_zone, а повторённый ads_cluster берётся
один раз. Несогласованные значения дают неизвестный спрос, а не сумму и не ноль.
Глобальные ads/idc и расчёт запаса в днях не изменены. Старый контрольный снимок
без кластерных полей перечитывается; формат checkpoint повышен до 2.
Миграция ставит существующий stock_cover на ближайшее обновление, сохраняя данные.

Соответствие SKU карточке проверяется через channel_skus.fbo. SKU FBS,
отображаемый артикул, название товара и распределение общего ads на доли
не используются. Если модель содержит несколько FBO SKU, нельзя подставить
ноль за неизвестный SKU в кластере. Нет cluster_name — показывается ID кластера.

## Данные WB и скорость

Кнопка «Загрузить направления» ставит отдельные задания по товарам с
подтверждёнными заказами из последнего общего FBO-отчёта. Она не отправляет
запросы маркетплейсу из API или браузера. Нет новых вызовов при открытии
главной, обычных рекомендаций или мобильного приложения.

В фоне: POST /api/v2/stocks-report/products/sizes, один nmID, stockType=wb,
includeOffice=true, 28 дней. Нативные officeID/regionName группируются по
региону. Варианты товара суммируются один раз; корневые offices и size.offices
не складываются повторно. Спрос — заказы за дни наличия, по тому же правилу,
что в существующем WB-расчёте. Неизвестные заказы/время наличия/остаток остаются
неизвестными. Дубликаты с разными цифрами не заменяют успешный снимок.

Лимитер общий с history/supply_demand: для поддерживаемых полноценных токенов
20 секунд, для базового токена 30 минут. При активной общей загрузке карточек
истории эти детальные задания уступают ей очередь. Поэтому полная детализация
большого магазина может быть долгой: 300 товаров — минимум около 100 минут
без конкурирующих запросов при интервале 20 секунд. Это ограничение текущего
нативного метода; первоначальная общая аналитика его не ждёт.

Готовые результаты видны постепенно, состояние не заменяется пустым экраном
при опросе. Кеш и задания переживают закрытие сайта. Готовые позиции обновляются
примерно раз в 6 часов с соблюдением очереди; на каждом запуске окно сдвигается
на последние 28 полных дней. Данные зашифрованы в supply_destination_snapshots
с AAD компании, кабинета и товара. Ошибка сохраняет предыдущую успешную версию.

Массовый STOCK_HISTORY_REPORT_CSV проверен 07.11.2026: официальная схема
из страницы API извлечена и сопоставлена с реальным ZIP-отчётом по двум товарам.
Создание, проверка состояния и скачивание вернули HTTP 200. Получено 10 строк:
RegionName, OfficeName, ChrtID, OrdersCount, StockCount, OfficeMissingTime
присутствуют. Значения продавца и ключи не записывались в артефакты.

OfficeID/warehouse_id в CSV отсутствуют. Поэтому он может ускорить получение
спроса и остатков, но не заменяет точные ID складов для вычета входящих партий.
В основной загрузчик CSV этим шагом не включён. Безопасное продолжение:
отдельный массовый снимок, подтверждённый справочник складов и дозагрузка
неразрешённых направлений текущим JSON-методом; приём неизвестных складов
как совпавших по похожему названию не допускается.

## Входящие партии

Составы уже существующих партий фильтруются по точному нативному ID конечного
склада. У WB сохраняется warehouseID, у Ozon storage_warehouse.warehouse_id.
Транзитный пункт и имя склада не используются для предположительного сопоставления.
Входящая партия вычитается только в соответствующем направлении и только по
тем датам/свежести, которые проходят общий фильтр SUPPLY_INCOMING.md.

Если конечный склад не известен среди складов отчёта, для количества входящих
остаётся null; уже подтверждённые поступления можно учитывать отдельно.
Нативный macrolocal_cluster_id не приравнивается к cluster_id без справочника.
Перемещений между кластерами код не предлагает и автоматически их не создаёт.

## API и планы

- GET /inventory/replenishment/destinations — список направлений выбранных кабинетов,
  суммы потребности, количество загруженных/ожидаемых товаров и состояние загрузки.
- POST /inventory/replenishment/destinations/refresh — запросить фоновое обновление,
  идемпотентно для уже ожидающих или свежих заданий. Требует inventory.read и CSRF.
- GET /inventory/replenishment и /export принимают destination_id совместно с
  одним store_id. Итоги считаются до фильтра срочности и пагинации.
- Создание плана принимает destination_id. Название направления определяется
  сервером, а не вводом клиента; весь состав берётся из готовых серверных фактов.
  Смена направления требует нового плана. Кратности, варианты, ручные количества,
  ревизии, CSV и заполнение исходного XLSX сохраняют существующий порядок работы.

Чтение направлений требует inventory.read; выгрузка — reports.export; создание
и редактирование планов — owner/admin. Все маршруты включены в fail-closed каталог
доступов. RLS снимков проверяет компанию, кабинет и разрешение; рабочие задания
содержат только маршрутизационные метаданные и перед каждым запросом повторно
проверяют актуального владельца/администратора и ключ, перед публикацией — ещё раз.
Новая миграция: 0031_supply_destinations. Новых библиотек нет.
