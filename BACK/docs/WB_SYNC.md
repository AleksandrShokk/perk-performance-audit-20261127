# Синхронизация WB: первая версия

Реализован слой загрузки. Товары, продажи/возвраты, остатки на складах WB и выбранные
поля финансового отчёта загружаются независимо. Начальный период: последние семь
завершённых дней по московскому времени. Общего ограничения в 31 день больше нет.
Продажи доступны за последние 90 календарных дней, включая сегодня; финансовая история
доступна с 29 января 2024 года. Сегодняшние сведения могут быть неполными.
При выборе общей длинной истории даты продаж ограничиваются последними 90 днями,
а финансы получают весь выбранный период. Фактические даты указаны в каждой задаче.

## Запуск и просмотр

`docker compose up -d --build` применяет миграцию `0003_wb_sync` и запускает api, worker, beat.
Владелец магазина с пройденной MFA вызывает
`POST /api/v1/workspaces/{workspace_id}/stores/{store_id}/sync` с телом:

```json
{"sources":["catalog","sales","stocks","finance"]}
```

Дополнительные поля: `date_from`, `date_to` (YYYY-MM-DD). Даты применяются к продажам и
финансам. Для одного источника укажите, например, `{"sources":["catalog"]}`.
202 — задачи приняты; 409 — такая загрузка уже выполняется.

Из корня проекта в активированном Python-окружении:

```sh
python -m scripts.sync_wb start
python -m scripts.sync_wb status
python -m scripts.sync_wb data --source catalog
```

Клиент читает PERK access token из `.secrets/perk-access-token.tmp`, использует обычный API
с проверкой MFA. При 401 нужен новый токен после входа. WB-токен используется сервером.
Workspace/магазин выбираются автоматически только если они единственные, иначе нужны
`--workspace UUID --store UUID`. Консоль показывает статусы и счётчики, без записей магазина.

- `GET .../sync-runs`: история.
- `GET .../sync-runs/{run_id}`: прогресс, страницы, ближайший повтор, код ошибки.
- `GET .../sync-capabilities`: тип токена, доступные источники и границы истории без секретов.
- `GET .../data/{source}?limit=50&offset=0`: записи, общее число, последняя успешная
  и последняя запущенная задачи, `is_partial`, `updated_at`.
  Доступны owner/viewer своего workspace с MFA.

Статусы: queued, running, succeeded, failed. Код ошибки у running означает ожидание
повтора. Отсутствие успешной загрузки не означает нулевые продажи. Деньги и большие ID
возвращаются строками для сохранения точности на JavaScript-фронтенде.

## Защита и восстановление

В очереди только ID задачи. Ключ WB расшифровывается перед каждой страницей внутри worker.
Используется фиксированный список официальных адресов WB с TLS, без редиректов и proxy из env.
Ответ ограничен 16 МиБ и временем чтения; ошибки WB и секреты в логах не сохраняются.
Из ответа сохраняются только разрешённые поля, поля покупателей и неизвестные поля отбрасываются.

Записи зашифрованы AES-GCM с привязкой к workspace, магазину, источнику и ключу записи.
RLS новых таблиц дополнительно ограничивает чтение членством в workspace, запись — owner.
Worker повторно проверяет активность инициатора, его MFA и роль владельца.

PostgreSQL хранит очередь ожидающих задач. Beat проверяет её каждые 15 секунд. Потерянная
задача возвращается в очередь через три минуты; повтор доставки не удваивает данные.
Состояние страниц сохраняется транзакционно. Redis ограничивает частоту запросов к WB
по продавцу и источнику; при отказе Redis внешние запросы не выполняются. 429 учитывает
Retry-After и X-Ratelimit-Retry. Reset используется только при их отсутствии: он означает
восстановление полного пакета запросов, а не время следующего разрешённого запроса.
Заголовки успешного ответа также учитываются, когда Remaining=0.
Временные ошибки повторяются с нарастающей задержкой
до восьми попыток. Доступность методов зависит также от типа токена и подписки WB.

При первой загрузке, пока нет успешного набора, API показывает зашифрованные промежуточные
строки той же задачи с явным `is_partial=true`. Это предварительный просмотр; такие данные
не подходят для итоговых расчётов. При последующих обновлениях остаётся виден предыдущий
полный набор до завершения новой загрузки. Сбой удаляет промежуточные строки.
Каталог и остатки заменяются атомарно;
продажи и финансы обновляются по стабильным ключам. Лимит загрузки — 250 000 строк,
5 000 страниц. Превышение завершает задачу ошибкой, не публикуя усечённые данные.

## Границы этой версии

- Каталог: действующие карточки, названия, артикулы, размеры и баркоды; без корзины.
- Остатки: текущие склады WB (FBW), по размерам, включая товары в пути. Новый метод требует
  **персональный или сервисный токен** с категорией «Аналитика». Базовый токен не поддерживается,
  поэтому запрос блокируется заранее с `wb_token_type_unsupported`; другие источники продолжают
  работу. Старый метод `/api/v1/supplier/stocks` удалён WB, запасного обхода через него нет.
  Собственные
  склады продавца (FBS) и история ежедневных снимков пока не реализованы.
- Продажи/возвраты: загрузка периода через flag=0 и точный lastChangeDate последней строки
  до пустого массива. Строки отбираются по дате события, а не дате изменения. Для превышающих
  лимит размера ответов или остановившегося курсора применяется безопасный переход на flag=1
  по дням. Ранее начатые посуточные задачи продолжаются со своего дня.
  Суммы предварительные, не равны прибыли
  или окончательной выплате. Перезагрузка обновляет ключи, но не удаляет исчезнувшие события.
- Финансы: daily-строки, rrdId/reportId, товар, операция, количество, дата, валюта,
  retailAmount, forPay, acquiringFee. Страница до 10 000 строк; загрузка продолжается
  до документированного 204. Защита ограничивает одну задачу 250 000 строками: очень большие
  истории нужно запрашивать несколькими периодами. Успешные периоды объединяются по rrdId.
  Все расходы, логистика/хранение, себестоимость, налоги и расчёт прибыли — следующий этап.
- Автоматическая ежедневная синхронизация ещё не включена: beat доставляет уже заказанные
  задачи. Обновление изменяемого периода запускается вручную.
- Сверка реальных сумм с кабинетом WB ещё необходима. Это не законченная финансовая отчётность.

Ошибки отдельных источников не отменяют остальные. `wb_access_denied` означает 403 WB,
`wb_subscription_required` — 402; нужен доступ к соответствующему методу на стороне WB.
