## 2. Каталог, первая загрузка и продажи — в работе

Состояние на 8 октября: работают загрузчики каталога, продаж/возвратов, остатков FBW и
финансовых отчётов, фоновые задачи, восстановление, шифрование, RLS и API просмотра.
Добавлены регулярное обновление, агрегаты по дням, график, ABC по количеству и защищённый
кэш. Для истории продаж за год и более используются финансовые отчёты; источники не
складываются между собой. См. [sales-history.md](sales-history.md) и [WB_SYNC.md](WB_SYNC.md).
Локальная консоль показывает данные реального магазина. Независимую сверку с отчётами WB
и проверку вместе с будущим фронтом/сгенерированным клиентом не считаем завершёнными.

1. Словарь метрик и проверочные примеры из исходных отчётов.
2. Каталог: модель → размер/цвет → карточка площадки; явное сопоставление артикулов.
3. Raw-слой WB, загрузчик каталога и заказов, затем продаж и возвратов.
4. Пагинация, лимиты, backoff, продолжение загрузки, уникальные ключи и защита от параллельного запуска.
5. Перезагрузка изменяемых периодов; журнал прогресса и ошибок.
6. API сводки, динамики по дням и продаж по товарам; фильтры и сравнение периодов.
7. Импорт Excel/CSV с предварительным просмотром, сопоставлением SKU и дедупликацией с API.
8. Явно обозначенный набор demo-данных для работы над фронтендом без реального магазина.

Критерий: цифры за выбранный период сверены с отчётом WB; повторная загрузка не меняет суммы
из-за дублей, ошибки API не уничтожают предыдущие данные. OpenAPI генерирует клиент Orval.

Остаются отдельными задачами: нормализованный каталог и сопоставление вариантов, заказы,
фильтры и сравнение периодов, полная типизированная схема ответа аналитики, импорт файлов и
demo-набор. Они не объявляются готовыми из-за появления тестовой консоли.
При подключении фронта обязательно сверить WB → API → график на одинаковом периоде;
проверить даты, валюты, возвраты, корректировки, полноту и права доступа.

## 3. Финансы, юнит-экономика и ABC — следующий основной этап, начат

8 октября: расширена проекция финансовых строк для комиссий, логистики, хранения,
приёмки, удержаний и корректировок. Схема API показывает версию данных и отсутствующие
суммы; старые неизвестные расходы остаются `null`. Это подготовка исходных фактов,
а не готовый расчёт прибыли. Порядок и ограничения — в [FINANCE.md](FINANCE.md).
Также реализованы Excel-шаблон, предпросмотр/применение истории себестоимости и отдельные
внешние расходы магазина. Общая цена артикула допускает отдельные цены размеров по баркоду;
для расчёта выбирается цена на дату события. Контракт — [COST_IMPORTS.md](COST_IMPORTS.md).
Подключены предварительная сводка/дни/товары и ABC по выручке и положительному вкладу
в прибыль, фоновые дневные факты и зашифрованный кэш. Неполные данные не получают
нулевую или выдуманную прибыль. Контракт — [PROFIT.md](PROFIT.md).
Далее: сверка специальных операций и налогов → подключение форм и графиков фронта.

1. Финансовые операции: продажи/возвраты, комиссии, логистика, хранение, приёмка, реклама,
   удержания и компенсации; отдельно несопоставленные расходы.
2. История себестоимости через Excel и дополнительные расходы магазина — ввод реализован.
3. Фактическая прибыль, маржинальность, движения денег и выплата — отдельные показатели.
4. Общие расходы учитывать отдельно на уровне магазина; по SKU произвольно не распределять.
   Отмечать предварительный результат при неполноте данных.
5. Калькулятор сценария SKU отдельно от фактического отчёта, настраиваемые налоговые параметры.
6. ABC по выручке, количеству и положительному вкладу в прибыль, настраиваемые пороги 80/95/100.
7. Убыточные/нулевые позиции отдельно; сравнение групп в сопоставимых периодах.

Критерий: Decimal-расчёты и примеры сверены; изменение закупочной цены сегодня не переписывает
историю; сумма групп согласуется с магазином. Налоговые формулы согласуются отдельно.

## 4. Ozon и общая аналитика

Отдельные клиенты Seller API, каталог, заказы, возвраты, финансы и остатки. Затем ручное/
проверяемое сопоставление вариантов WB/Ozon и общие отчёты. Performance API — отдельное подключение.
Критерий: сумма отчётов площадок совпадает с объединённым отчётом при одинаковых определениях метрик.

## 5. Склады и планирование поставок

Снимки остатков, резервы, собственный склад, товары в пути и ожидаемые даты поступления.
Базовый прогноз учитывает дни наличия товара, сроки доставки, покрытие, страховой запас,
упаковку и доступный остаток на собственном складе. Новые товары допускают ручной прогноз.
План возвращает вариант → склад → количество → дату → объяснение расчёта.
Сезонность и ограничения приёмки добавляем после проверки простого прогноза.
Критерий: товар не распределяется дважды по разным складам; позднее поступление не скрывает
дефицит до даты поступления; общий FBS-остаток для WB/Ozon не удваивается.

## 6. Продвижение и рекомендации

Загрузка кампаний, расходов, показов, кликов, заказов и доступных результатов. CTR, CPC,
конверсии и явно определённые виды ДРР. Разделение прямой и смежной атрибуции.
Сначала рекомендации обычным кодом: расход выше допустимого, низкий запас при рекламе,
ухудшение результатов, недостаточно данных. Каждая рекомендация объясняет период и цифры.
ИИ-объяснение остаётся экспериментом: только поверх проверенных расчётов и после оценки пользы.

## 7. Размещение и обслуживание

Авторизация на всех бизнес-маршрутах, HTTPS, резервные копии, тест восстановления,
ограничения запросов, мониторинг ошибок и загрузок, миграции в CI, журнал действий.
Прежде чем менять схемы API, проверять генерацию типов и совместимость клиентов.

## Бэклог

- Внешняя аналитика: доступные публичные данные конкурентов или лицензированный источник;
  сначала исследование источников, условий использования и точности оценок.
- Нельзя считать падение чужих остатков доказанными продажами.
- Сложные прогнозы и автоматическая оптимизация рекламы — после накопления проверенной истории.
- ИИ-консультант по подготовленным агрегатам; без самостоятельного изменения ставок/поставок.
