# Мобильные поставки

Отдельный экран «Поставки»: вкладки «Рекомендации» (по умолчанию) и «Поставки WB».
Доступен из «Ещё» и карточки поставок на главной. Экран остатков содержит только остатки.
Новой нижней вкладки, конструктора кластеров/коробов, изменения поставок WB и
имитации созданных на сайте планов нет.

## API

- GET `/api/v1/workspaces/{workspace_id}/inventory/replenishment`
- GET `/api/v1/workspaces/{workspace_id}/inventory/supplies`

Оба читают сохранённые данные; GET не вызывает WB. Общие параметры: `store_id`,
`limit` (0–100), `offset`. Расчёт дополнительно принимает `urgent_only`.
Итоги считаются до пагинации и фильтра срочности. `inventory.read`, RLS и разрешённые
сотруднику магазины применяются до чтения и суммирования. Финансов и себестоимости
в новых ответах нет. Ключи запросов фронта включают пользователя, пространство,
магазин и права; ответы не сохраняются на диск.

## Потребность

Источник `supply_demand`: тот же исторический отчёт, что у запаса в днях, но
**stockType=wb**, только FBO. Текущий общий `stock_history` (FBO+FBS) не меняется.
Окно — 28 завершённых московских дней, обновление раз в 6 часов. Оба чтения
одного WB endpoint используют общий лимит продавца, включая Basic 30 минут.

Среднесуточные заказы = заказанные единицы / дни наличия.
Остаток к поступлению = max(0, остаток FBO − среднесуточные заказы × 7).
Потребность = ceil(max(0, среднесуточные заказы × 30 − остаток к поступлению)).
Отсутствовавший до поступления товар не превращается в накопленные заказы.
Срочные позиции — текущий запас не более 7 дней, включая распроданные товары
с подтверждённым положительным спросом.

Это оценка по артикулам WB, без округления до коробов, распределения по размерам
и вычета оформленных поставок в пути. Значения 30/7/7 заданы на сервере;
сложные настройки и редактирование остаются для сайта. Метод и ограничения
доступны через InfoHint, а не развёрнутые сноски на экране.

Ноль заказов не создаёт искусственную потребность. Неизвестные заказы, остатки,
длительность наличия или отсутствующие строки исключаются с `partial=true`.
Нет успешного отчёта — итоги null, а не ноль. В главной срочность берётся из
этого же источника, прежний локальный inventory/forecast там больше не используется.

## Готовые поставки

Источник `supplies`, категория ключа «Поставки», обновление каждый час.
Загружаются все активные поставки и принятые за последние 30 дней, с пагинацией
по 1000. Затем — детали каждой поставки отдельными фоновыми задачами с лимитами
WB. Состав поставки и упаковка не загружаются на этом этапе.

Карточки рекомендаций и поставок WB открывают детали. Показаны номер, пункт, дата,
количество, принятое количество и исходный статус WB:
черновик, запланирована, можно отгружать, отгружена, идёт приёмка, принята.
Отказ показывается отдельно. Идентичность по preorderID при его наличии остаётся
стабильной после выдачи supplyID. API только читает; поставки не создаются и не меняются.
Телефоны, финансовые коэффициенты и стоимость приёмки не сохраняются.

Публикация обоих источников атомарная. Ошибка или неполная пагинация сохраняет
предыдущий успешный снимок; подтверждённый пустой ответ очищает прежние строки.
Отсутствие права не блокирует остальную страницу. После замены ключа существующая
логика credential_changed возобновляет план с исправленными правами.
