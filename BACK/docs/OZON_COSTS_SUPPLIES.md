# Ozon: себестоимость, рекомендации и общие FBS

История предыдущего этапа. Текущее состояние: [OZON_PARITY.md](OZON_PARITY.md).

## Доступные функции

- График показывает фактические суммы покупки без префикса «от» по просьбе пользователя.
  partial_amounts остаётся в API и запрещает сравнивать неполные денежные итоги как полные.
- Карточка хранения за 30 дней не зависит от готовности поставок. Суммируются только
  статьи хранения, без приёмки, по существующему финансовому источнику Ozon.
- Рекомендации FBO Ozon используют опубликованные available/ads за 28 дней.
  Количество считается общей с WB функцией: запас на 30 дней после поступления,
  7 дней на доставку/приёмку, без округления до коробов и без вычета оформленных поставок.
  Противоречивый SKU или неизвестный спрос не превращаются в ноль. Известный нулевой спрос
  не создаёт рекомендацию. Это план PERK по исходным данным Ozon, а не копия плана из ЛК.
- Ozon имеет feature supplies для рекомендаций. История оформленных поставок — отдельный
  supply_history, пока WB. На Ozon не показывается пустая вкладка «Поставки WB».

## FBS: явная настройка вместо догадки

GET/PUT /workspaces/{id}/inventory/settings: fbs_mode separate/shared, без строки — unknown.
При separate общая сводка WB/Ozon складывает FBS и FBO+FBS. При unknown/shared сводка
FBS ждёт явного соответствия физического склада и товаров: одинаковые остатки нельзя
просто сложить или взять максимум. Отдельные кабинеты остаются доступны.
Настройка меняется владельцем/администратором через «Остатки → Учёт складов FBS».
Читатели видят только метаданные учёта, не чужие остатки. Подтверждение пользователя
«Разные склады» применяется отдельным одноразовым скриптом только к единственному
подходящему подключённому пространству. Универсальное значение для всех пользователей
не зашивается в код или миграцию. Полнота/свежесть и неизвестные цены сохраняются.
Общая оборачиваемость разных методик WB/Ozon по-прежнему не усредняется.

## История себестоимости

Новая marketplace_variant_costs хранит версию по workspace/store/neutral variant UUID/
currency/effective_from. Деньги зашифрованы с AAD, содержащим весь ключ. FORCE RLS:
profit.read для чтения, costs.write для записи, плюс доступ к конкретному кабинету.
Ozon SKU не записывается в nm_id/chrt_id WB. Сохранение проверяет принадлежность
варианта опубликованному каталогу данного кабинета. Повторы/одновременные сохранения
обрабатываются атомарным upsert. Существующая история WB не меняется.

GET/PUT /workspaces/{id}/stores/{id}/variant-costs: типы генерируются из OpenAPI.
В приложении используется тот же редактор карточки и та же история цен. Себестоимость
учитывается в каталоге и оценке запасов FBO/FBS; неполная сумма имеет cost_complete=false.

## Расчёт прибыли Ozon

Начисления дополняются cost_basis=accrual_v1 и подписанными cost_items (SKU, количество,
валюта, HMAC отправления). Новая миграция повторно планирует Ozon finance, не очищая отчёты.
Положительные продажи используют себестоимость на дату финансовой операции. Возврат
обращает себестоимость исходной продажи, найденной по отправлению/SKU, а не текущую цену.
Если дата/вариант неизвестны или несколько исходных дат имеют разные цены,
прибыль остаётся неизвестной. Неизвестные варианты считаются уникально, не по числу строк.
Читатели profit.read получают доступ к таблице исходных цен/дат реализации для этого
расчёта; она не содержит комиссии, себестоимости или PII. График без analytics.read
по-прежнему недоступен.

Внешние расходы поддерживают существующие идемпотентные API расходов для Ozon.
Они уменьшают прибыль, но не меняют сумму начислений Ozon к перечислению.
Внешняя реклама включается в общий рекламный блок и не дублируется во внешних расходах.
Прибыль до налогов появляется при покрытом периоде, известной себестоимости и отсутствии
неразобранного остатка начислений. Расходы приводятся к одной базе во смешанной сводке.
finance.read без profit.read не получает себестоимость, производные расходы с ней или прибыль.
Налоговая оценка и подробная товарная экономика Ozon — следующий отдельный этап.

## Проверки и развёртывание

Проверяются исходные цены/даты, варианты, стоимость остатков, возвраты при смене цены,
идемпотентные внешние расходы, роли/скоупы/RLS, настройки FBS и нативные рекомендации.
Реальный дневной ответ: 258 начислений, 39 товарных операций, 2 возврата, отсутствующих
количеств нет. Компоненты финансового итога сошлись без остатка.
Общая бухгалтерская сверка по-прежнему отложена по договорённости с пользователем.

При обновлении сначала остановить старые worker/beat/API, затем применить 0027 и запустить
новые процессы. Дефолт FBS не меняется миграцией. Перед публикацией импорты заново проверяют
ключ/права/run_id; загрузка с предыдущим форматом не должна перезаписать новые cost_items.
Подготовка каталогов/финансов остаётся фоновой, внешние API не вызываются в запросе экрана.
