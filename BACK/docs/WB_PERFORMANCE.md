# Быстрый экран и фоновая загрузка WB

## Что исправлено

- Снят искусственный общий предел 31 день. Продажи: последние 90 дней. Финансы: с 29.01.2024.
- Продажи загружаются целым периодом с точным курсором изменения вместо одного запроса на день.
- Финансовая страница увеличена с 1 000 до 10 000 строк; защищённый размер ответа остаётся 16 МиБ.
- Первый импорт показывает первые полученные строки с пометкой «набор неполный».
- Базовый WB-токен сохранён. Остатки заранее отмечены недоступными для этого типа.
- Уже загруженные записи читаются из PostgreSQL; открытые страницы кешируются в памяти вкладки.
- Пауза WB выбирается по Retry, а не по более длинному Reset полного пакета запросов.

## Почему первый импорт не может быть моментальным

WB задаёт частоту запросов и может возвращать 429 с паузой в несколько часов. Размер каталога,
число финансовых строк и тип токена влияют на время. Перезапуск PERK или повышение числа
работников не снимают ограничения продавца. Существующие паузы не сбрасываются этим обновлением.
В интерфейсе показано время следующего запроса и реальные даты активной задачи.

Максимальная история означает поддерживаемые даты. Полнота реальных данных зависит от истории
магазина и доступности метода WB. Сверка сумм с кабинетом ещё нужна. Одна задача ограничена
250 000 строками; при большем объёме историю делят на несколько периодов, результаты объединяются.

## Следующий шаг для почти мгновенного дашборда

1. После подключения магазина сначала загружать последние 7–30 дней, чтобы быстро получить
   полезный экран. Остальную историю догружать небольшими периодами в фоне.
2. Включить отдельный планировщик обновлений: продажи — изменения с последнего курсора с
   перекрытием нескольких дней, финансы — новые и изменяемые отчётные периоды. Каталог — реже.
   Частоту выбирать по фактическим заголовкам WB. Сейчас автоматического регулярного обновления
   магазина нет; beat только доставляет вручную запрошенные загрузки.
3. После полной публикации считать агрегаты по дню и SKU: количество, возвраты, предварительные
   суммы; отдельно итоговые финансовые показатели. ABC считать по согласованной метрике.
4. Кешировать уже рассчитанный ответ в Redis с привязкой к workspace, магазину, периоду и версии
   данных. Включать все фильтры и права доступа в ключ, не помещать туда WB-токены. При обновлении
   инвалидировать только затронутые периоды. Определить допустимую задержку актуальности.
5. Фронт сначала показывает сохранённый ответ, затем обновляет его в фоне. Всегда видна дата
   актуальности и пометка о незавершённом импорте. Цель для локального чтения — сотни миллисекунд;
   это целевой показатель, а не обещание времени первого импорта.

Этот путь даёт быстрый интерфейс без частых обращений к WB и без снижения защиты магазина.
