# Параметры потребности FBO

GET /api/v1/workspaces/{workspace_id}/inventory/replenishment принимает target_days
(1–180, по умолчанию 30) и lead_time_days (0–90, по умолчанию 7). Параметры меняют
прогноз по готовым данным и не запускают запросов к площадкам.

Источники сохранены: WB — спрос по заказам за дни наличия из нативной истории FBO;
Ozon — нативные среднесуточные продажи FBO. Ставки спроса не смешиваются и не
подменяются финансовой выручкой. Общее количество — сумма отдельных кабинетов.

Расчёт:

- Остаток к поступлению = max(остаток FBO − спрос в день × срок доставки, 0).
- Потребность = max(ceil(спрос в день × целевой запас − остаток к поступлению), 0).
- К поставке = ceil(потребность / кратность короба) × кратность короба.

Например: 100 шт., спрос 5 шт./день, доставка 7 дней, запас 30 дней.
Остаток к поступлению 65 шт., потребность 85 шт. При коробе 6 шт. довезти 90 шт.
Дефицит до поступления не становится заказами, которые нужно исполнить задним числом.
Оформленные и находящиеся в пути поставки пока не вычитаются.

PUT /api/v1/workspaces/{workspace_id}/stores/{store_id}/inventory/packaging/{product_key}
с телом {"box_multiple":6} сохраняет правило 1–10000 шт. на короб. Изменение разрешено
owner/admin, чтение — inventory.read. Ключ WB — nm_id, Ozon — стабильный product.id,
связанный с нативной карточкой. Разные кабинеты не делят настройки автоматически.
RLS и составной FK ограничивают компанию и кабинет. Значение 1 отменяет округление.
В строках ответа quantity — округлённое количество, required_quantity — до округления,
box_multiple — применённое правило. Итоги считаются до фильтра срочности и пагинации.

GET /api/v1/workspaces/{workspace_id}/inventory/replenishment/export принимает те же
параметры и фильтры, отдаёт CSV всех строк без лимита страницы. Нужны inventory.read
и reports.export. Заголовки запрещают кеширование, идентификаторы не теряют нули,
потенциальные формулы продавца/маркетплейса экранируются. Частичность и время
обновления отражены в файле; отсутствие готового расчёта даёт 409.

CSV является отчётом потребности. Он не выдаётся за шаблон импорта WB/Ozon:
проверенные форматы и автоматический расчёт
по кластерам будут отдельными этапами. Результаты этого шага не создают поставки на площадках.


## Сохранённые планы

На сайте «Поставки → Планы» хранятся внутренние планы отдельно от рекомендаций
и оформленных поставок маркетплейса. Один план принадлежит одному кабинету.
Название склада/кластера вводится пользователем; оно не перераспределяет спрос.
Для разных назначений создаются отдельные планы. Их количества не вычитаются
из рекомендаций: статус «Готов» не означает оформленную поставку на площадке.

- POST /workspaces/{wid}/stores/{sid}/inventory/plans: title, destination,
  target_days, lead_time_days, urgent_only. Снимок включает все страницы выбранного
  кабинета и фильтра, до 5000 позиций. Пустая/неготовая рекомендация — 409.
- GET /workspaces/{wid}/inventory/plans: кабинет и серверная пагинация.
- GET /workspaces/{wid}/inventory/plans/{id}: сохранённый снимок.
- PUT /workspaces/{wid}/inventory/plans/{id}: revision, title, destination,
  status (draft/ready/archived), полный список product_key/quantity. Нулём исключают
  позицию из поставки. Идентификаторы, описание, спрос и короб сервер берёт только
  из сохранённого снимка. Менять состав через произвольные идентификаторы нельзя.
- GET /workspaces/{wid}/inventory/plans/{id}/export: CSV сохранённых ненулевых
  количеств со складом, названием и параметрами. Это внутренний отчёт потребности,
  а не проверенный шаблон загрузки в WB/Ozon.

recommended_quantity хранит исходное округлённое предложение; quantity — выбор
пользователя. Кратность короба фиксируется при создании плана. Обновления каталога,
спроса и правил упаковки не изменяют уже сохранённые планы. Если нужен свежий
расчёт, создаётся новый план. Состав и название зашифрованы общим Vault с AAD
компания/кабинет/план; чувствительные снимки не попадают в localStorage.

Чтение требует inventory.read; экспорт дополнительно reports.export. Изменения
разрешены owner/admin. RLS и составной FK ограничивают компанию и кабинет.
Строка блокируется на время записи; устаревшая revision даёт 409 без потери
чужих изменений. Все ответы сохраняют запрет кеширования.

## Размеры и штрихкоды планов

При создании плана сервер читает существующий общий каталог кабинета без
себестоимости, остатков и сетевых запросов к площадке. В каждой строке сохраняется
variants: variant_id, external_id, size, barcodes, выбранный barcode, quantity.
Это те же стабильные ID, что в каталоге товаров; WB nm_id и Ozon product.id
не сопоставляются между собой. Модели и объединения цветов не придумываются.

Если размер один, ему автоматически назначается количество строки. Если размеров
несколько, начальные количества нулевые: спрос по размерам текущий источник не
даёт, поэтому равномерное распределение не используется. Единственный штрихкод
выбирается автоматически; из нескольких пользователь выбирает один. Правило
короба пока применяется к сумме одной карточки, как на предыдущем этапе.

PUT плана принимает необязательные items[].variants с variant_id/quantity/barcode.
Если массив передан, он должен содержать ровно сохранённые ID без повторов.
Метаданные размеров клиент не меняет. Количества — целые 0..2147483647; сумма
размеров не может превышать количество строки. Неполное распределение и пустой
штрихкод разрешены в черновике. Старые запросы без variants продолжают работать;
для единственного размера количество синхронизируется с количеством строки.

PlanSummary/PlanView дополнены allocated_quantity, allocation_complete,
allocation_error. Общая выгрузка /export сохранена. Новая /items-export
(operationId supplyPlanItemsExport) выдаёт CSV только при полном распределении
каждой строки, выборе принадлежащего ей штрихкода и отсутствии повторов штрихкодов
между ненулевыми позициями. Иначе 409. Количества не переносятся из одной карточки
в другую даже при совпадении штрихкода. Нулевые размеры в файл не включаются;
длинные идентификаторы, нули и текстовая защита CSV сохранены.

Ранее созданные зашифрованные снимки читаются с variants=[]. POST
/workspaces/{wid}/inventory/plans/{id}/variants (supplyPlanVariantsLoad) с revision
подгружает размеры только в строки без вариантов; ранее сохранённые варианты
и распределение остаются неизменными. Повторная/устаревшая revision и отсутствие
новых размеров дают 409. Новая запись увеличивает revision и создаёт audit-событие.
Новая миграция не нужна: совместимость обеспечена значениями по умолчанию.

Изменения и подгрузка размеров — owner/admin, inventory.read. Детальная выгрузка
дополнительно требует reports.export. Используются прежние RLS, блокировка строки,
шифрование и запрет кеширования. На сайте загрузка размеров и выгрузки недоступны
до сохранения правок; закрытие окна отменяет запрос и игнорирует поздний ответ.

В редакторе строки раскрываются кнопкой «Размеры». Поиск учитывает размеры и
штрихкоды, форма сохраняет данные при переходах между страницами. Ошибка на другой
странице возвращает к нужной позиции. Валидация строит индекс товаров один раз,
а поиск и схема повторно используются при редактировании количества.

Детальный CSV остаётся внутренним отчётом. Исходные XLSX WB/Ozon заполняются
отдельным обработчиком ниже. Расчёт по направлениям и входящие партии описаны
в SUPPLY_DESTINATIONS.md и SUPPLY_INCOMING.md.


## Заполнение исходного XLSX

На сайте в сохранённом плане доступна кнопка «Заполнить XLSX». Пользователь
загружает актуальный исходный файл площадки, проверяет лист/столбцы и скачивает
заполненную копию. Подсказка разметки — предложение по известным заголовкам,
а не утверждение о конкретной версии шаблона WB/Ozon. Можно выбрать другой лист,
строку заголовков и первую строку товаров. Дополнительные настройки свёрнуты.

API: /workspaces/{wid}/inventory/plans/{id}/template.

- POST /inspect (supplyTemplateInspect), multipart file. Ответ содержит fingerprint
  файла, revision плана, листы/возможные заголовки, допустимые типы идентификаторов,
  первые три позиции и общий объём для проверки, предлагаемую разметку.
- POST /fill (supplyTemplateFill), тот же multipart file и query: sheet,
  header_row, first_row, identifier_column, quantity_column, identifier_type,
  mode, revision, digest, data_digest. Возвращает XLSX с no-store. Изменившийся
  план, файл или набор идентификаторов — 409, неправильный файл/разметка — 422.

Обе операции только читают план: нужны inventory.read и reports.export,
включая сотрудников с этими правами. Классификация явно внесена в READ_RULES
несмотря на метод POST (тело содержит файл). RLS кабинета, CSRF, сессия, rate limit
и действующие проверки компании сохранены. Новых таблиц/миграций нет.

Идентификатор WB — выбранный штрихкод конкретного размера. У Ozon дополнительно
доступны точный offer_id и нативный FBO SKU из channel_skus.fbo текущего каталога.
Один SKU должен однозначно принадлежать одному product.external_id; общий
marketplace_code или SKU FBS вместо него не используются. Если SKU неоднозначен,
данный способ выгрузки недоступен. data_digest защищает от незаметного изменения
каталога между проверкой и скачиванием. Для выгрузки по offer_id/FBO SKU выбранный
штрихкод не обязателен, но количества по размерам должны полностью совпадать с
сохранённым планом. Дубли выбранного идентификатора не объединяются молча.

Режим append («Пустой шаблон») заполняет пустую область после заголовков,
копирует оформление первой строки и обновляет dimension/autoFilter при наличии.
Если в области уже есть данные, операция отклоняется. Для пустой форматированной
Excel-таблицы tablePart добавление строк пока не поддерживается.

Режим match («Товары из плана, остальные — 0») находит существующие строки по
точному идентификатору, проставляет количества плана и нули в остальных товарных
строках выбранной области. Колонки описания/склада и все остальные данные остаются.
Каждая позиция плана должна найтись ровно в одной строке. Пропуски/повторы,
нечисловые количества и объединённые ячейки в области данных блокируют файл.
Область должна быть обычной таблицей товаров без итогов/сносок после первой
строки данных; сложные формы упаковки/коробов отдельными блоками не поддерживаются.

Workbook изменяет только два выбранных столбца одного листа. Остальные ZIP-части,
их параметры сжатия, пространства имён, стили, комментарии и другие листы
сохраняются. Идентификаторы записываются как inlineStr, количества — как числа;
нули в начале/длинные значения не округляются и не становятся формулами.

Файл до 256 КБ; multipart allowance до 320 КБ только на двух новых точных маршрутах,
прежний лимит остальных API 64 КБ и allowance финансового импорта не изменены.
Распаковка ограничена 12 МБ/128 частей; DTD, внешние связи, макросы, исполняемые
вложения, ячейки с формулами и неверные ZIP/XML-координаты не принимаются.
До 20 листов, 100000 ячеек на листе, 10000 позиций плана, 20000 строк заполнения.
Файлы не сохраняются в базе/на сервере; повторная отправка для скачивания — новый
ограниченный запрос. В браузере File хранится только внутри открытого окна,
не передаётся в переменные кешируемой мутации и не записывается в localStorage.

JSON-ошибка файлового запроса разбирается из Blob с ограничением 64 КБ, при этом
сохраняются HTTP-статус и данные step-up. Пользователь видит причину отказа,
а не только общее сообщение скачивания. Закрытие окна отменяет запрос и игнорирует
поздний ответ; вход в заполнение доступен только после сохранения правок плана.

Проверка включала реальные структуры Excel, созданные независимым openpyxl:
стили, длинные штрихкоды, тип количества, комментарий, скрытый лист, ширина колонок
и диапазон фильтра сохранены. Это техническая проверка обработки XLSX. Приём файла
самой площадкой не проверялся; для этого нужен актуальный файл конкретного кабинета
и отдельная проверка в ЛК. Код не создаёт поставки в WB/Ozon и не отправляет им файл.

самой площадкой и оформление поставки этим шагом не выполнялись.
