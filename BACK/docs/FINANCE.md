# Финансы и юнит-экономика

## Первый шаг: сохранить исходные финансовые факты

8 октября 2026: финансовый загрузчик запрашивает расширенный набор полей
`POST /api/finance/v1/sales-reports/detailed`. Источник и пагинация остаются прежними.
Официальное описание: <https://dev.wildberries.ru/docs/openapi/financial-reports-and-accounting>.

В `/api/v1/workspaces/{workspace_id}/stores/{store_id}/data/finance` доступны:

| Поле PERK | Поле WB |
|---|---|
| `sales_commission` | `ppvzSalesCommission` |
| `delivery_service` | `deliveryService` |
| `paid_storage` | `paidStorage` |
| `paid_acceptance` | `paidAcceptance` |
| `penalty` | `penalty` |
| `deduction` | `deduction` |
| `additional_payment` | `additionalPayment` |
| `rebill_logistic_cost` | `rebillLogisticCost` |
| `pickup_reward` | `ppvzReward` |
| `wb_remuneration` / `wb_remuneration_vat` | `vw` / `vwNds` |
| `cashback_amount` / `cashback_commission_change` | `cashbackAmount` / `cashbackCommissionChange` |
| `installment_cofinancing_amount` | `installmentCofinancingAmount` |
| `retail_price` / `retail_price_with_discount` | `retailPrice` / `retailPriceWithDisc` |

Также сохраняются артикул продавца, размер, баркод, склад, даты заказа/продажи и `srid`.
Поля `retail_amount`, `for_pay`, `acquiring_fee` и дата отражения `report_date` сохраняются.
Все денежные значения — строки Decimal. Знак исходного значения не изменяется: отрицательная
коррекция расхода не должна превращаться в новый положительный расход. `nm_id = "0"` допустим:
расход магазина без привязки к товару нельзя терять или распределять произвольно.

## Полнота и старые записи

- `data_version = 1`: прежняя ограниченная проекция. Добавленные поля возвращаются как `null`.
- `data_version = 2`: загрузчик запросил расширенные поля; это само по себе не гарантирует полноту.
- `missing_amount_fields`: какие из запрошенных сумм отсутствуют или равны `null` в строке.
- `requested_amounts_complete`: все запрошенные суммы получены; явный `"0"` считается известной суммой.

Эти признаки описывают строку отчёта, а не готовность расчёта прибыли, всех расходов магазина
или рекламной аналитики. Названия операций сохраняются без неподтверждённой классификации.
Удержания не считаются автоматически расходами на рекламу.

Ранее загруженные расходы нельзя восстановить из сокращённой проекции. Они появятся для периода
после его повторной загрузки. Автоматическая загрузка обновляет недавние периоды; полную историю
расходов нужно будет догрузить отдельно. Обновление строки по `rrd_id` заменяет её без дублей,
при ошибке загрузки опубликованные данные сохраняются. Данные шифруются с привязкой к workspace,
магазину, источнику и идентификатору строки; остаются проверки доступа и MFA.

Пакет начинается со 100 000 строк. Если ответ превышает установленный предел 64 MiB, существующий
механизм уменьшает размер следующего запроса, сохраняя курсор и лимиты WB. Размер ответа и объём
памяти не увеличиваем ради более широкого набора полей.

## Себестоимость и внешние расходы — реализован ввод данных

Себестоимость загружается через Excel: скачать шаблон → заполнить → получить предпросмотр
с ошибками по строкам → применить целиком. Баркод необязателен: пустой задаёт общую цену
артикула, заполненный — цену конкретного размера/варианта. При расчёте сначала выбирается
цена баркода, действующая на дату события, затем общая цена артикула. Новая цена имеет
собственную дату начала действия; существующая цена на ту же дату не перезаписывается.
Отсутствующая цена возвращается как `null`, а явно заданная нулевая — как известный ноль.

Дополнительный расход магазина — отдельная запись: сумма, дата, валюта и комментарий.
Он учитывается в сводке магазина за период; по товарам автоматически не распределяется.
Повтор отправки с тем же `request_id` не создаёт второй расход. Удаление логическое,
с сохранением журнала действия. Суммы разных валют не складываются без согласованных правил.

Новые цены, предпросмотры и суммы/комментарии расходов зашифрованы. Действуют MFA,
разделение workspace/магазинов и RLS; изменять данные может только владелец.
Подробный контракт для фронтенда: [COST_IMPORTS.md](COST_IMPORTS.md).

`/costs/calculate` уже выбирает цену по дате и варианту и считает себестоимость количества.
Эти цены подключены к новым `/finance/summary` и `/finance/abc`: сводка, дни для графиков
и предварительный вклад товара в прибыль. Возвраты восстанавливают себестоимость исходной
продажи; списания учитываются отдельно. Формулы, признаки неполноты и контракт —
[PROFIT.md](PROFIT.md). Интерфейс графиков ещё предстоит подключить на фронте.

## Следующие шаги

1. Сверить знаки и состав финансовых операций с примером отчёта WB; отдельно показывать
   неизвестные операции и расходы без SKU. Не суммировать перекрывающиеся поля дважды.
2. Сверить предварительную прибыль и ABC с исходным отчётом, включая специальные операции.
3. Налоги, сценарии себестоимости и закрытие отчётных периодов; отдельно фактические
   движения денег. `for_pay` не является чистой прибылью или подтверждением банковской выплаты.
4. Подключить импорт, графики и ABC на фронте. Налоговые правила согласуются отдельно.

Рекламные расходы, налоговый расчёт и распределение общих затрат по товарам пока не реализованы.
Формулу «for_pay минус все поля расходов» использовать нельзя: часть удержаний уже входит
в перечисляемые суммы. Нужны проверочные примеры продаж, возвратов и корректировок.

## Проверка при подключении будущего фронта

- Сгенерировать клиент и типы из актуальной OpenAPI; проверить строки денег и nullable-поля.
- Сверить один и тот же период в WB, API и графиках: даты событий и отражения в отчёте отдельно.
- Проверить валюты, возвраты, корректировки, неполную историю, неизвестную себестоимость и расходы.
- Повторная загрузка не меняет итог из-за дублей; изменение цены не переписывает закрытую историю.
- Проверить недоступность чужих workspace/магазинов, сессии и MFA на настоящем клиенте.
