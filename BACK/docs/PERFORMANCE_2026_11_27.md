# Скорость сайта: правки от 27.11.2026

## Что изменено

| Что | Где | Зачем |
|---|---|---|
| Замер времени каждого запроса API | `app/core/timing.py`, `app/main.py`, `app/db/session.py`, `app/security/crypto.py` | Видно, сколько времени уходит на SQL, на расшифровку и на остальное |
| 3 процесса API вместо одного | `deploy/compose.production.yaml` (`WEB_CONCURRENCY`) | Дашборд шлёт ~8 запросов параллельно, а один процесс Python считает их по очереди на одном ядре |
| Кэш финансового отчёта и графиков живёт дольше 15 мин (с пятой итерации: 3 ч и 2 ч) | `app/modules/finance/report.py`, `app/modules/sync/analytics.py` | Ключ кэша содержит ревизию данных, поэтому старые цифры показаны не будут. Раньше после 15 минут без заходов любое открытие сайта пересчитывало отчёт с нуля |
| Попадание в кэш больше не перешифровывает и не перезаписывает отчёт | там же | Минус одно шифрование и одна запись в Redis на каждое открытие |
| Ключ AES-GCM готовится один раз, а не на каждую строку | `app/security/crypto.py` | Мелочь: 1.5 → 0.6 мкс на строку. Замер показал, что само шифрование быстрое и вряд ли даёт секунды |
| `pg_stat_statements` и `track_io_timing` | `deploy/compose.production.yaml` (postgres) | Точный топ медленных SQL-запросов |

Что сознательно **не** менялось:

- **Частота Celery Beat.** После каждой страницы загрузки WB задача ждёт следующего тика
  `perk.sync.dispatch` (каждые 2 с). Если сделать 10 с, первичная загрузка года станет
  медленнее. Нагрузка от опроса на сервере ничтожная: load average 0.2.
- **Настройки PostgreSQL** (`random_page_cost` и подобные). База 393 МБ целиком в памяти,
  кэш попадает в 98% случаев — эффекта не будет.

## Как выкатить

На сервере, после того как новые файлы `BACK/` и `deploy/` лежат в `/opt/perk`:

```bash
cd /opt/perk/deploy
```

```bash
./compose.sh build api
```

Пересоздать postgres: у него новые параметры запуска. База перезапустится на несколько
секунд, лучше делать вечером.

```bash
./compose.sh up -d --wait --force-recreate postgres
```

Пересоздать **все** контейнеры бэкенда, а не только API. Сейчас `worker`, `worker-ozon`
и `beat` работают на образе от 15 ноября, старее API.

```bash
./compose.sh up -d --wait --force-recreate api worker worker-ozon worker-heavy beat
```

Один раз включить расширение, от админ-пользователя PostgreSQL:

```bash
./compose.sh exec postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "CREATE EXTENSION IF NOT EXISTS pg_stat_statements;"'
```

Откат: вернуть прошлую версию `compose.production.yaml` и образ. Миграций базы нет.

Количество процессов API задаётся переменной `API_WORKERS` (по умолчанию 3). Если памяти
мало, поставьте 2.

## Как смотреть замеры

### В браузере (самый простой способ)

1. Откройте сайт, нажмите F12 и перейдите на вкладку **Network** (Сеть).
2. Обновите страницу. В фильтре выберите **Fetch/XHR**.
3. Кликните любой запрос `/api/v1/...` и откройте вкладку **Timing**. Внизу будет блок
   **Server Timing**:
   - `db` — время в PostgreSQL и число SQL-запросов;
   - `crypto` — расшифровка и шифрование;
   - `app` — всё остальное в Python: расчёты, сборка JSON;
   - `total` — весь запрос на сервере.

Если `total` маленький, а запрос в браузере долгий — дело в сети или во фронтенде.
Если большой — видно, какая часть тормозит.

### В логах сервера

Каждый запрос дольше 1 секунды пишется одной строкой, без идентификаторов и данных:

```
slow_request method=GET route=/api/v1/workspaces/{workspace_id}/finance/overview status=200 total_ms=4210 db_ms=950 sql=63 crypto_ms=2400 crypto_ops=1800
```

Собрать за день:

```bash
./compose.sh logs --since 24h api | grep slow_request
```

Порог меняется переменной `SLOW_REQUEST_MS`.

### Топ медленных SQL

После включения `pg_stat_statements` и часа обычной работы:

```sql
SELECT calls, round(total_exec_time) AS total_ms, round(mean_exec_time, 1) AS mean_ms,
       left(query, 120) AS query
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 20;
```

Эти три источника и покажут, что делать дальше: кэш агрегата `/business`, перенос
расшифровки или переделку записи метрик при загрузке.

## Вторая итерация (по замерам с продакшена)

Замеры Server-Timing из браузера и `pg_stat_statements` показали три узких места.

| Что | Было | Причина | Правка |
|---|---|---|---|
| График воронки | 4.5–5 с | `product_labels.enrich`: для 1–3 товаров вне каталога искал артикул продавца перебором **всех** записей воронки (`split_part(record_key)` не использует индекс). Это 4.2 с на запрос, и время росло с историей, а лимит — 5 с | Поиск ограничен днями отчёта (не больше 31 последнего) через диапазон первичного ключа. Если запрос всё же упадёт, отчёт отдаётся без подписи, а не с ошибкой |
| Остатки (`/inventory/overview`) | 1.2–1.8 с, 2–3 раза на странице | Каждый запрос заново расшифровывал и собирал ~12 тыс. строк | Готовый ответ кэшируется в Redis (зашифрован, общий для всех процессов API) |
| Товары (`/products`) | 0.4–0.9 с | То же на ~1100 строках | То же |

Кэш ответов (`app/core/response_cache.py`) берёт ключ из «отпечатка» входных данных:

- последняя успешная синхронизация каждого источника. Записи каталога, остатков, цен, FBS и истории остатков целиком заменяются при её публикации;
- флаги идущей загрузки;
- число и время последней записи себестоимости (себестоимость только добавляется);
- название магазина, дата и признак «данные старше 2 дней».

Новые данные, себестоимость или запущенная загрузка дают новый ключ, поэтому устаревший ответ не показывается. Поиск по тексту хранится 10 минут, остальное — 3 часа (с пятой итерации). С пятой итерации кэшируется и часть WB в выборке «все магазины».

Осталось на следующий шаг: построчная проверка доступа (RLS, функция `perk_store_access`) стоит ~45 мкс на строку. Например, `count(*)` по `inventory_snapshots` в `store_revision` — 168 мс. Это изменение в базе, касающееся безопасности, его нужно делать отдельно и с тестами.

## Третья итерация

После второго патча график стал 1.65 с (было 4.6 с), а первый расчёт остатков всё ещё занимал 1.4–2.6 с. Профиль на локальном стенде (1100 товаров, ~12 тыс. строк остатков) показал:

- остатки читались и расшифровывались дважды за запрос: внутри списка товаров и в самих остатках. Теперь в пределах одного запроса каждый источник читается один раз (`sync.read.read_once`): 25 тыс. расшифровок стало 14 тыс.;
- карточки позиций (варианты, склады, pydantic-модели) строились для всех ~1100 товаров, а показываются 10–20. Теперь строятся только для запрошенной страницы, итоги по-прежнему считаются по всем;
- подписи товаров в графике: найденный артикул продавца запоминается на сутки, «не найдено» — на час и только для того же периода.

Стенд, первый расчёт остатков: 0.99–1.62 с → 0.61–1.19 с; повторный — 13–20 мс.

Следующий резерв — построчная проверка доступа (RLS). Функция `perk_store_access` вызывается на каждую строку (`SECURITY DEFINER` + `SET search_path`, не встраивается): ~24 мкс на строку на стенде и ~44 мкс на продакшене (`FETCH FORWARD 5000` = 220 мс). Если заменить её в политиках на проверку по заранее вычисленному списку доступных магазинов (один раз на запрос), все тяжёлые чтения ускорятся примерно вдвое. Это изменение политик безопасности и миграция — делать отдельно.

## Четвёртая итерация: проверка доступа один раз на запрос

Миграция `0044_set_based_store_access`. Политики RLS 35 таблиц сравнивают строку с набором пар (рабочее пространство, магазин), доступных текущему пользователю (`perk_accessible_stores()`). Набор вычисляется один раз на SQL-запрос (`hashed SubPlan`), а не через вызов `perk_store_access()` на каждую строку.

- Стенд, 50 тыс. строк: 800 мс → 12 мс (без RLS — 8 мс).
- Права не меняются: в тестах `tests/integration/test_store_access_policies.py` старая функция построчно согласна с новыми политиками для владельца, менеджера с ограничением по магазинам, менеджера без ограничений и постороннего; запись в чужой магазин отклоняется.
- Таблица `stores` оставлена на старой функции: создаваемый магазин ещё не входит в набор.
- Новые таблицы в будущих миграциях лучше сразу писать в новом виде:
  `USING ((workspace_id, store_id) IN (SELECT a.workspace_id, a.store_id FROM public.perk_accessible_stores() a))`.
- Откат: `alembic downgrade 0043_phone_change` возвращает политики посимвольно (проверено).

Redis: в продакшен-compose добавлены `--maxmemory 192mb --maxmemory-policy volatile-lru`. Раньше при росте кэшей контейнер мог быть убит по лимиту памяти 256 МБ вместе с очередью задач.
