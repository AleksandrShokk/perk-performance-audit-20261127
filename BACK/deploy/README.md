# PERK на собственном сервере

Структура: `/opt/perk/BACK`, `/opt/perk/FRONT`, `/opt/perk/deploy`, `/opt/perk/backups`.
Содержимое этой папки копируется в `/opt/perk/deploy`; соседние BACK и FRONT содержат исходники.

`compose.production.yaml` дополняет базовый `BACK/compose.yaml`. `compose.sh` передаёт точные пути и отдельное имя проекта `perk-production`, поэтому локальные и тестовые базы не затрагиваются.

## Подготовка

1. Ubuntu 24.04, Docker Engine и Compose; наружу разрешены только 22, 80 и 443.
2. Запись A домена направлена на сервер. Caddy получает и обновляет HTTPS-сертификат автоматически.
3. `production.env` создан из примера, хранится только на сервере с правами 0600.
4. Пароли БД/Redis, SMTP и Telegram Gateway находятся в `BACK/.secrets/`. Папка имеет права 0700; отдельные файлы доступны только явно подключённым контейнерам.
5. При переносе старой базы обязательно перенесите прежний `security.json`: без него нельзя расшифровать токены магазинов, TOTP и резервные коды.
6. Базу восстанавливают только в заранее проверенную пустую БД. ACL из pg_dump сохраняют: не используйте `pg_restore --no-privileges`. Ограниченная роль `perk_app` должна существовать до восстановления. После него запускается `scripts.migrate`.

## Запуск

```bash
./compose.sh build api web
./compose.sh up -d --wait postgres redis
# Сначала восстановление свежей базы и проверка миграции/числа записей.
./compose.sh up -d --wait api web worker worker-ozon worker-heavy beat
# Только после проверки домена, SMTP, Telegram и приложения:
./compose.sh --profile public up -d --wait proxy
```

Порты API и Next удалены из публичной конфигурации. PostgreSQL и Redis работают во внутренней сети. API доверяет заголовкам посетителя только от адреса Caddy `10.93.0.2`; прокси заменяет входящий X-Forwarded-For адресом клиента.

`APP_ENV=production`: защищённые cookies, явные HTTPS origins/hosts, отсутствие документации API и тестовых отправщиков. Свободная регистрация закрыта; существующие пользователи входят, новые сотрудники регистрируются по приглашениям. Включение публичной регистрации — отдельное решение: `PUBLIC_REGISTRATION_ENABLED=true` в окружении API.

## Резервные копии

`backup.sh` создаёт согласованный pg_dump и отдельный архив ключей/настроек с правами 0600. `perk-backup.timer` запускает ежедневное копирование; на сервере хранятся семь дней. Эти файлы содержат частные данные и никогда не входят в Git.

Копии на том же VPS не защищают от потери всего сервера. Нужна отдельная копия на другом устройстве/хранилище. После первого переноса копия скачивается на компьютер владельца; постоянное внешнее хранилище подключается отдельно.

При переносе приложение и загрузчики старого экземпляра останавливают, сохраняя исходную базу. Старые браузерные сессии и одноразовые коды на новом экземпляре отзывают; пользователи входят заново. Данные магазинов и права сотрудников сохраняются.

Для регистрации владельца при закрытой бете можно задать `REGISTRATION_ALLOWED_EMAILS` как JSON-список разрешённых email в приватном production.env. Публичная регистрация при этом остаётся закрытой, приглашённые сотрудники регистрируются как раньше. После первоначальной настройки список можно вернуть к `[]`.


## Временный тест персональных токенов WB

По умолчанию production принимает только сервисные токены PERK. Для закрытого
тестирования внутри компании можно указать UUID её кабинетов в
`WB_PERSONAL_TOKEN_TEST_WORKSPACES` (JSON-массив) и срок в
`WB_PERSONAL_TOKEN_TEST_UNTIL` (ISO 8601 с часовым поясом). Например:

```dotenv
WB_PERSONAL_TOKEN_TEST_WORKSPACES=["00000000-0000-0000-0000-000000000001"]
WB_PERSONAL_TOKEN_TEST_UNTIL=<REDACTED>
```

Разрешается только персональный токен (`acc=3`, `for=self`), только для чтения,
с действующим сроком и разрешёнными категориями. WB дополнительно проверяет токен
и продавца при подключении. Права сотрудников, MFA и изоляция кабинетов сохраняются.
Проверка применяется также к фоновым загрузкам. После указанного срока исключение
перестаёт действовать. Чтобы отключить его раньше, очистите массив и пересоздайте
API и workers. Применение этой настройки не требует миграций или очистки базы.

Это режим внутреннего тестирования компании, не способ подключения сторонних
продавцов облачного сервиса. Для внешних клиентов требуется подходящий тип токена
по правилам WB.

Закрытая бета может временно принимать персональные read-only токены во всех компаниях:
`WB_PERSONAL_TOKEN_TEST_ALL_WORKSPACES=true` вместе с обязательным будущим
`WB_PERSONAL_TOKEN_TEST_UNTIL`. После срока исключение выключается автоматически.
Для самостоятельной регистрации на тот же срок: `PUBLIC_REGISTRATION_ENABLED=true`
и `REGISTRATION_OPEN_UNTIL` с датой и часовым поясом. Приглашения действуют и после
закрытия публичной регистрации. Проверки владельца токена и прав чтения сохраняются.
