# Ozon и WB: общие функции мобильного приложения

Обновление 5 ноября 2026. Текущий расчёт запаса в днях оставлен без изменений:
WB — история наличия и заказы за 28 дней; Ozon — нативные FBO idc/ads.
Запас FBS Ozon и общий запас в днях двух площадок не вычисляются.

## Что добавлено для Ozon

| Раздел | Поведение |
| --- | --- |
| Воронка | Просмотры карточек, добавления в корзину, конверсии просмотр → корзина, корзина → заказ, просмотр → заказ |
| Налоги | Общая форма, датированные настройки, существующий расчёт НДС/налога/чистой прибыли |
| Себестоимость | Excel-шаблон с SKU Ozon, проверка файла, предпросмотр, подтверждение и история датированных цен |
| Товарные финансы | Общие страницы выручки/прибыли, лидеры продаж, финансовые показатели по товарам и API юнит-экономики |
| Поставки | Вкладка «Оформленные», детали, статусы и фильтр кабинета, включая общую сводку WB/Ozon |

Заказы/выкупы и деньги графика сохраняют прежний источник: отправления Ozon,
фактическая цена покупателя с учётом скидок площадки. Финансы читаются из начислений.
Название товара/склада не используется для подстановки недостающих связей.

## Воронка и фоновая загрузка

- Новый независимый источник `traffic`: `/v1/analytics/data`, измерение `day`,
  метрики `hits_view_pdp` и `hits_tocart`. Запросы ограничены общим для Client ID
  интервалом не менее 61 секунды. Квота/ошибка аналитики не блокирует заказы или финансы.
- Сначала загружаются 7 дней, далее история до 90 дней порциями по 28 дней.
  При выборе более старого периода очередь расширяет историю. Затем последние
  56 завершённых дней обновляются раз в 6 часов без открытого приложения.
- Итоги просмотров/корзин и конверсии доступны после покрытия выбранного периода.
  Подтверждённый пустой день равен нулю; ошибка/отсутствующий день остаётся неизвестным.
- Доступ к метрикам зависит от прав ключа и подписки Ozon. Избранное не подменяется
  нулём: соответствующей метрики в подключённом методе нет, `wishlist=null`.
- Цена покупателя всё ещё может быть неизвестна для части FBO. Частичные денежные
  итоги не используются как полные при сравнении периодов.

## Финансы и себестоимость

- `finance_details` включает Ozon в общие товарные финансовые страницы.
  Товары используют нейтральный `id`, `marketplace=ozon`, `marketplace_code=SKU`;
  Ozon SKU никогда не записывается в WB `nm_id`.
- Начисления содержат `details_basis=accrual_products_v1`. Только строки с нативным
  SKU попадают в товар. Общие услуги без SKU остаются в `unassigned`; распределения
  пропорционально выручке/названию нет. Сумма товарных строк и нераспределённых
  начислений совпадает с исходным денежным итогом.
- Комиссия берётся из начисления Ozon. Разница между фактической ценой покупателя
  и выплатой продавцу не считается комиссией: скидку может финансировать Ozon.
- Внешние расходы учитываются один раз, без произвольного распределения по товарам.
  Общая сумма расходов включает комиссию, услуги, внешние расходы и известную
  себестоимость. При неизвестной себестоимости полный итог/прибыль не выдумываются.
- Excel использует SKU Ozon, необязательный баркод, цену, дату начала и валюту.
  Проверяются принадлежность SKU/баркода кабинету, числа/даты, дубли и конфликты цен.
  До применения цены не меняются. Предпросмотр действует 30 минут; повторное
  применение возвращает тот же результат. Проверка каталога/конфликтов повторяется
  при подтверждении. Файл ограничен 5000 строками, существующие ограничения XLSX сохранены.
- Возврат обращает себестоимость исходной продажи, а не текущую цену.
  Налоговая оценка использует общий калькулятор; при смене настройки внутри периода
  неподтверждённый налог не выдаётся за точный результат.
- Сводки финансов могут содержать выручку продавца; график заказов и товарная
  цена используют фактическую цену покупателя. Эти разные базы не обязаны совпадать.

## Оформленные поставки

Источники: `/v1/supply-order/status/counter`, `/v3/supply-order/list`,
`/v3/supply-order/get`, `/v1/supply-order/bundle`. Это чтение кабинета;
приложение не создаёт поставку на площадке.

Все активные поставки и последние 180 дней завершённых/отменённых сохраняются
зашифрованным снимком. Количество складывается из содержимого bundle, статусы
приводятся к общему формату, плановая дата учитывает часовой пояс склада.
Если склад назначения не указан, показывается нативный кластер. Пункт сдачи
не подменяет склад назначения. Фактическая дата приёмки и принятое количество
остаются неизвестными, когда подключённый источник их не отдаёт.

Обновление раз в час; проверенное содержимое неизменившейся завершённой поставки
повторно проверяется не реже чем раз в 6 часов. Большая загрузка продолжается
с зашифрованного промежуточного состояния. При ошибке остаётся предыдущий
успешный снимок. Рекомендации пополнения и их формулы не изменены.

## Архитектура и права

- Клиенты внешних методов: `app/integrations/ozon/traffic.py`, `supplies.py`.
- Снимки/задачи/чтение: `app/modules/insights/extra_models.py`, `extra_jobs.py`,
  `ozon_traffic.py`; общий диспетчер `ozon_jobs.py`.
- Товарный финансовый адаптер: `app/modules/finance/ozon_report.py`;
  общий импорт вариантов: `variant_import.py`.
- Миграция `0028_ozon_parity` добавляет снимки и фоновые источники, инициирует
  обновление товарного состава начислений. Существующие данные не очищаются.
- Проверка владельца/админа, текущего ключа и run ID выполняется до обращения
  к площадке и перед публикацией. Чужой/устаревший запуск не меняет готовый снимок.
- RLS ограничивает снимки магазином и правами `analytics.read`/`inventory.read`.
  Финансовые данные без `profit.read` не раскрывают себестоимость/прибыль.
  `costs.write` уже включает чтение прибыли согласно общим зависимостям прав;
  импорт не создаёт отдельную несовместимую систему разрешений.
- На клиенте переиспользованы существующие формы налогов/Excel и страницы отчётов.
  Расчётов маркетплейса в интерфейсе нет. Новые библиотеки не потребовались.

## Границы и следующие шаги

Бухгалтерская сверка с ЛК остаётся отдельной задачей. Новая функциональность
не устраняет неизвестные исходные цены и не создаёт метрику избранного Ozon.
Рекламная аналитика, связывание одинаковых товаров между площадками и ручной
прогон на физических iOS/Android остаются отдельными этапами.

Авторизация общая для площадок. Ранее проверенные исправления сохранены;
Telegram/SMS в локальной разработке остаются тестовыми по решению пользователя.
До закрытой беты нужно настроить настоящую доставку кодов.

## Проверка обновления

В изолированной базе с миграциями с нуля прошли 602 серверных теста. После
завершающей корректировки минутного расписания traffic повторно прошли 11
интеграционных сценариев этого этапа. Приложение: 194 теста, ESLint и TypeScript.
Ruff/проверка форматирования и Bandit без замечаний; локальный экспорт
Android/iOS/web успешен. Физические устройства в этой работе не проверялись.

Миграция 0028 применена к локальному серверу; аккаунты/ключи/готовые отчёты сохранены.
На подключённом Ozon подтверждены реальные просмотры/корзины, 42 оформленные
поставки на момент проверки и готовый товарный отчёт последних 7 дней.
Новые товарные начисления вместе с нераспределёнными строками сходятся с исходным
итогом начислений. Фоновая подготовка завершена без ошибок: просмотры/корзины за
90 дней и товарные начисления за 181 сохранённый финансовый день. Реальные
закупочные цены и налоговые настройки вручную не подставлялись. Бухгалтерская сверка всей истории
с ЛК остаётся отложенной по договорённости.
